[[config-driven-architecture]]
== Config-Driven Architecture

**Structure in code. Content in config. Behavior emerges from definitions.**

=== The Pattern

[source]
----
┌─────────────────────────────────────────────────────────────┐
│ CONFIG (Data)                                               │
│   What something IS — definitions, rules, identity          │
├─────────────────────────────────────────────────────────────┤
│ CODE (Logic)                                                │
│   How to USE the config — processing, execution             │
├─────────────────────────────────────────────────────────────┤
│ BEHAVIOR (Emergence)                                        │
│   What HAPPENS — config + code = runtime behavior           │
└─────────────────────────────────────────────────────────────┘
----

=== Config Per Layer

[cols="2,4,4",options="header"]
|===
| Layer | What Config Defines | What Code Does

| *OmniCode*
| Grammar rules, type definitions, transpilation mappings
| Parse according to grammar, transpile according to mappings

| *MillenniumOS*
| Trit-byte table, Scripture encoding table, system parameters
| Convert using tables, lookup using encodings

| *CPI-SI*
| Identity (config.jsonc, bio.md), capabilities, boundaries
| Load identity, apply to cognition, respect boundaries

| *FaithNet*
| Tiered access rules, protocol mappings, verification criteria
| Route according to tiers, map according to protocol
|===

=== Why Config-Driven Matters

[cols="2,4",options="header"]
|===
| Benefit | How It Works

| *Multiple instances from same code*
| CPI-SI code is generic; config makes each instance unique

| *Update without recompile*
| Change tiered access rules in config, FaithNet behavior changes

| *Explicit definitions*
| What's blocked isn't buried in code — it's declared in config

| *Auditable*
| Config files ARE the source of truth — grep them, validate them

| *Separation of concerns*
| Architects define config, code applies it
|===

=== Config as Anchor

Config-driven maps to the building block methodfootnote:[Building Block Method: Foundation (0) → Build Up (+1) → Break Down (-1)]:

[cols="2,2,4",options="header"]
|===
| Component | Role | Building Block

| *Config*
| The fixed definition
| Anchor (0)

| *Code building up*
| Construct behavior FROM config
| Build Up (+1)

| *Validation breaking down*
| Verify behavior AGAINST config
| Break Down (-1)
|===

**The test:** Can you trace runtime behavior back to config? Yes = config-driven. No = hardcoded.

[[polyglot-system]]
== Polyglot System

**Right tool for each job. Not everything in one language.**

=== Three Language Categories

[source]
----
DATA LANGUAGES          SYSTEM LANGUAGES        APPLICATION LANGUAGES
───────────────         ────────────────        ─────────────────────
TOML                    C                       Go
JSONC                   Rust                    Rust
JSON                    C++
YAML

Config, definitions     Low-level primitives    Integration, logic,
Tables, lookups         System operations       networking, patterns
----

=== Why Polyglot?

[cols="2,4",options="header"]
|===
| If we write... | We prove...

| Everything in one language
| That language works (not the concepts)

| System-level in C/Rust, application in Go
| Concepts work across language boundaries

| Data in TOML, system in C, application in Go
| *Each component optimal for its purpose*
|===

[IMPORTANT]
====
*If everything is Go, we've just proven Go works* — not that the concepts are universal. The polyglot approach proves the concepts transcend any single language.
====

=== Language Selection Rationale

[cols="2,2,4",options="header"]
|===
| Component Type | Best Languages | Why

| *Config/Data*
| TOML, JSONC, JSON
| Human-readable, parseable, declarative

| *System-level*
| C, Rust
| Close to metal, no GC, precise memory control

| *Application*
| Go, Rust
| Good networking, concurrency, clean patterns
|===
