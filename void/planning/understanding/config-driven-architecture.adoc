[[config-driven-model]]
== Config-Driven Model

The config-driven model is the architectural foundation enabling Kingdom Technology. Rather than behavior hardcoded in source, #behavior is defined by configuration files# that are loaded dynamically. Everything propagates from a single source of truth.

[%collapsible%open]
.What Config-Driven Means
====
In traditional architecture, behavior is scattered across source code. Changing behavior requires finding and modifying code, recompiling, and redeploying. Each system maintains its own definitions.

In config-driven architecture:

[cols="2,4",options="header"]
|===
| Aspect | Config-Driven Approach

| *Behavior Definition*
| Declared in configuration files, not hardcoded in source

| *Loading*
| Configuration is loaded dynamically at runtime

| *Propagation*
| Changes to config automatically propagate to all consumers

| *Single Source*
| One authoritative definition, many consumers
|===

*Key principle:* Static config, dynamic loading, automatic propagation. The config IS the truth - code reads from it, never defines it independently.
====

[[how-deep-this-goes]]
=== How Deep This Goes

To understand why OmniCode must exist first, consider the filesystem itself:

[%collapsible%open]
.The Filesystem Example
====
Even something as fundamental as filesystem operations requires configuration-driven architecture at every level:

[cols="2,4,3",options="header"]
|===
| Layer | What Needs Config | Why It Matters

| *Paths*
| Directory structure, naming conventions
| Every tool must navigate the same way

| *Permissions*
| Read/write/execute rules
| Security model must be consistent

| *File Types*
| Extensions, MIME types, handlers
| Tools must recognize and process files correctly

| *Metadata*
| Timestamps, ownership, attributes
| Tracking and auditing across systems

| *Operations*
| Create, read, update, delete behaviors
| CRUD operations must behave predictably
|===

If the filesystem isn't config-driven, nothing built on top can be. Each layer depends on consistent behavior from the layer below.

*The insight:* This depth applies to EVERY subsystem. Config-driven isn't a feature - it's the foundational architecture that makes everything else possible.

<<_top,↑ Back to Top>>
====

[%collapsible]
.The Propagation Pattern
====
When config changes, everything that consumes it must update. This is the propagation patternfootnote:[Propagation pattern: Changes to a source automatically flowing to all dependent systems]:

----
┌─────────────────────────────────────────────────────────────┐
│                    CONFIG SOURCE (OmniCode)                 │
│                                                             │
│   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐     │
│   │ definitions │   │    types    │   │   schemas   │     │
│   └──────┬──────┘   └──────┬──────┘   └──────┬──────┘     │
└──────────┼─────────────────┼─────────────────┼────────────┘
           │                 │                 │
           ▼                 ▼                 ▼
    ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
    │ MillenniumOS │  │    CPI-SI    │  │   FaithNet   │
    │   (reads)    │  │   (reads)    │  │   (reads)    │
    └──────────────┘  └──────────────┘  └──────────────┘
----

*The discipline:* Systems NEVER define these things locally. They always read from the central config. This is what makes parallel design possible.

<<_top,↑ Back to Top>>
====

[%collapsible%open]
.The Cascade Pattern (Learned Through Alignment Work)
====
When you reorganize the source, you create debt at EVERY reference point. This is the cascade patternfootnote:[Cascade pattern: Changes at the source propagate through every dependent reference - if you move a file, every link to it needs updating]:

[cols="2,4",options="header"]
|===
| Action | Cascade Effect

| *Move a file*
| Every reference to that file needs updating

| *Rename a section*
| Every link to that section needs updating

| *Change a template*
| Every file derived from that template may need alignment

| *Restructure a folder*
| Every navigation path needs recalculation
|===

*Mitigation:*

* *Grep before assuming* — Search for references before moving/renaming
* *Calculate depths* — Count `../` for each file's depth from target
* *Work in passes* — Update all references in a coordinated sweep
* *Track derivation* — Know what derives from what (the `derives_from` pragma)

*Key insight:* This isn't a problem to avoid — it's architectural reality. Config-driven means changes propagate. The discipline is managing that propagation, not preventing it.

[[parallel-design]]
== Parallel Design

Parallel designfootnote:[Parallel design: Designing interconnected systems simultaneously so they inform each other during formation] means designing interconnected systems simultaneously, so they inform each other during formation rather than after.

[%collapsible%open]
.What Parallel Design Enables
====
Traditional approach (sequential):

----
Build OmniCode → Complete
  Then build MillenniumOS → Complete
    Then build CPI-SI → Complete
      Then build FaithNet → Complete
        Then integrate → Discover incompatibilities → Rebuild
----

Parallel approach (with shared config):

----
┌───────────────────────────────────────────────────────────┐
│                    OmniCode (Core First)                  │
│                  ↓ defines contracts ↓                    │
├───────────────────────────────────────────────────────────┤
│  MillenniumOS  │     CPI-SI     │      FaithNet          │
│   (parallel)   │   (parallel)   │      (parallel)        │
│                │                │                         │
│  ← inform each other through shared contract →           │
└───────────────────────────────────────────────────────────┘
----

*Key benefit:* Systems inform each other DURING design. When MillenniumOS discovers a need, it's reflected in OmniCode. CPI-SI and FaithNet immediately see it. Integration is built-in, not bolted-on.

<<_top,↑ Back to Top>>
====

[[the-enabling-sequence]]
=== The Enabling Sequence

[%collapsible%open]
.What Must Be Established First
====
Parallel design requires certain foundations before others can proceed:

[cols="^1,2,4",options="header"]
|===
| Order | Component | Why It Must Come First

| 1️⃣
| *OmniCode Core Syntax*
| Can't write config without the language

| 2️⃣
| *Type System*
| Systems need types to define their contracts

| 3️⃣
| *Schema Definitions*
| Structures that use the types

| 4️⃣
| *Interface Contracts*
| How systems talk to each other

| 5️⃣
| *Validation Rules*
| How to verify compliance
|===

Once these five are established, MillenniumOS, CPI-SI, and FaithNet can proceed in parallel - all reading from and contributing to the same OmniCode definitions.

[TIP]
====
*Think of it like construction:* You can build walls, plumbing, and electrical in parallel once the foundation and blueprints exist. OmniCode is the blueprints. The core syntax is the foundation.
====

<<_top,↑ Back to Top>>
====

[[the-formation-pattern]]
=== The Formation Pattern

[%collapsible]
.Deep Dive: How Systems Form Together
====
The parallel design pattern follows a specific formation:

. *Define in OmniCode* — A new capability is specified in OmniCode
. *Systems Read* — Each system reads the new definition
. *Systems Implement* — Each implements what the definition means for them
. *Systems Inform* — Implementation reveals needs back to OmniCode
. *OmniCode Updates* — Definition refined based on feedback
. *Cycle Continues* — All systems evolve together

This is the config-driven model in action: OmniCode is the source of truth, systems are consumers that also inform the source.

*The biblical parallel:*

[quote, Genesis 1:1-2]
____
In the beginning God created the heaven and the earth. And the earth was without form, and void...
____

God spoke (the Word/definition), and creation formed according to that Word. OmniCode speaks definitions, and systems form according to those definitions. The Word precedes and shapes the formation.
