[[overview]]
== Overview

MillenniumOS is architecturally ternary — it thinks in base-3 (-1, 0, +1) while running on base-2 (binary) hardware. This document specifies the **mapping layer** that bridges these two worlds: the trit-bytefootnote:[Trit-byte: A ternary byte — the fundamental unit of ternary data, analogous to byte in binary systems] architecture.

[IMPORTANT]
====
*The mapping layer is #foundational#.* Everything else in MillenniumOS builds ON this layer. Get this wrong, everything above is wrong. Get this right, everything above has solid ground.
====

// # T.1 The Mapping [MAPPING]

//	Ternary to binary mapping — the foundational bridge

[[the-mapping]]
== The Mapping

MillenniumOS thinks in ternary (-1, 0, +1) but runs on binary hardware (0, 1). The mapping layer bridges this gap.

=== Ternary Values

[cols="^1,2,3",options="header"]
|===
| Value | Name | Building Block Role

| *-1*
| Negative
| Break Down (toward foundation)

| *0*
| Neutral
| Foundation/Anchor (the immutable center)

| *+1*
| Positive
| Build Up (from foundation)
|===

The building block method IS the operating logic: `-1 + 0 + 1 = 0` — balanced system.

=== Trit-to-Byte Mapping

**Single byte (8 bits) holds 5 trits:**

[cols="2,2,3",options="header"]
|===
| System | Capacity | Calculation

| *Ternary (5 trits)*
| 243 states
| 3^5 = 243

| *Binary (8 bits)*
| 256 states
| 2^8 = 256

| *Gap*
| 13 states
| 256 - 243 = 13
|===

**The 13 WEB variants fill the exact gap.** Not coincidence — design.

=== Packed vs Unpacked

[cols="1,2,2,2",options="header"]
|===
| Mode | Representation | Use Case | Trade-off

| *Unpacked*
| 1 byte per trit
| Computation (fast access)
| Simple but wasteful

| *Packed*
| 5 trits per byte
| Storage/transmission
| Efficient but requires encode/decode
|===

The system breathes — compressing and expanding as data moves:

```
Storage (packed) → decompress → Memory (unpacked) → compute → compress → Transmission (packed)
```

[[omnicode-requirements]]
== OmniCode Requirements

The mapping layer scopes what OmniCode needs FIRST.

=== The 5 Required Features

[cols="^1,2,3",options="header"]
|===
| Priority | Feature | Why Needed

| 1
| *Trit type*
| The fundamental ternary unit (-1, 0, +1)

| 2
| *Bit operations*
| Interface with binary hardware below

| 3
| *Pack/Unpack*
| Encode (KJV direction) / Decode (WEB direction)

| 4
| *Lookup/Index*
| Scripture table access operations

| 5
| *Ternary arithmetic*
| Math operations on trits
|===

=== What This Means

The 9 abstract language design questions collapse to 5 concrete features — exactly what's needed to build the mapping layer.

[IMPORTANT]
====
*OmniCode's first implementation is scoped by MillenniumOS's mapping layer requirements.* Not abstract language design — concrete need.
====

=== Implementation Order

```
1. Define trit type in OmniCode
         ↓
2. Implement bit operations (binary interface)
         ↓
3. Build pack/unpack (KJV/WEB encoding)
         ↓
4. Create lookup operations (Scripture index)
         ↓
5. Implement ternary arithmetic
         ↓
6. Mapping layer complete → build rest of OS
```

[[biblical-foundation]]
== Biblical Foundation

[NOTE]
====
*Why Genesis 1:6?* God created a firmament to divide waters above from waters below — a layer that separates and connects two different realms. The trit-byte mapping layer does exactly this: it divides and connects ternary logic and binary hardware.
====

_"And God said, Let there be a firmament in the midst of the waters, and let it divide the waters from the waters."_ — *Genesis 1:6 KJV*

*Applied:* Just as the firmament enables the waters above and below to exist in their proper realms while remaining connected through it, the mapping layer enables ternary logic to exist above binary hardware while translating between them. The firmament is foundational architecture — without it, the system collapses. So too with the trit-byte layer.
