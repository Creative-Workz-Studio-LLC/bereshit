[[five-families]]
== Five Math Operation Families

Phase 2 adds 38 math functions organized into 5 families. Each family serves a distinct purpose in balanced ternary computation.

[[family-1-arithmetic]]
=== Family 1: Arithmetic

*Carry-aware addition and subtraction.* Unlike simple trit_add from Phase 1, these handle overflow with explicit carry.

[cols="2,4",options="header"]
|===
| Function | Purpose

| `trit_hadd(a, b)` | Half adder: 2 trits → sum + carry
| `trit_fadd(a, b, c)` | Full adder: 3 trits → sum + carry
| `trit_hsub(a, b)` | Half subtractor: a - b → diff + borrow
| `trit_div(n, d)` | Integer division with sign handling
| `trit_negate_math(v)` | Arithmetic negation (distinct from trit_negate)
|===

[[family-2-comparison]]
=== Family 2: Comparison

*Ternary comparison returning trit.* Not boolean — full ternary result!

[cols="2,4",options="header"]
|===
| Function | Purpose

| `trit_cmp(a, b)` | Compare trits: -1 (a<b), 0 (a=b), +1 (a>b)
| `trit5_cmp(a, b)` | Compare packed trit5_t values
|===

[[family-3-conversion]]
=== Family 3: Conversion

*Transform between representations.* Bridge the trit world and integer world.

[cols="2,4",options="header"]
|===
| Function | Purpose

| `trit_to_int(t)` | Trit → integer (-1, 0, +1)
| `int_to_trit(i)` | Integer → trit (clamps to range)
| `stored_to_true(s)` | Byte (0-255) → health (-100 to +100)
| `true_to_stored(t)` | Health (-100 to +100) → byte (0-255)
|===

[[family-4-normalization]]
=== Family 4: Normalization

*Health levels with semantic meaning.* 7 levels from Perfect (+3) to Broken (-3).

[cols="2,4",options="header"]
|===
| Function | Purpose

| `trit_base_round(v, base)` | Round to ternary base (3, 9, 27)
| `trit_normalize(v)` | Clamp to valid range [-121, +121]
| `trit_level(v)` | Map value to health level (-3 to +3)
| `level_name(lvl)` | English name ("Perfect", "Whole", etc.)
| `level_hebrew(lvl)` | Hebrew name ("Tamim", "Shalem", etc.)
| `level_emoji(lvl)` | Visual indicator (💛, 💚, etc.)
|===

[[family-5-calculus]]
=== Family 5: Calculus

*Change detection over time.* These are inherently temporal — they track how values change.

[cols="2,4",options="header"]
|===
| Function | Purpose

| `trit_difference(prev, curr)` | Direction of change: -1/0/+1
| `trit_rate(delta, time)` | Rate of change as trit
| `trit_accumulate(acc, value)` | Running total with overflow protection
| `trit_threshold(value, threshold)` | Value vs threshold as trit
| `trend_direction(history, count)` | Overall trend from history array
|===

[TIP]
====
*Why calculus is temporal:* Difference compares NOW to BEFORE. Rate measures change OVER TIME. Trend projects PAST into FUTURE. These operations naturally integrate with the TIME layer from Phase 1.
====
