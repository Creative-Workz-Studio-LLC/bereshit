== Document Purpose

This document establishes *Accessible by Design* as CWS's fifth core value — the commitment to making everything understandable and usable by regular people, not just experts.

[.lead]
*"Understandable by regular people."*

[quote, 1 Corinthians 14:9 (KJV)]
____
So likewise ye, except ye utter by the tongue words easy to be understood, how shall it be known what is spoken? for ye shall speak into the air.
____

== Anti-Patterns

=== Complexity Worship

[sidebar]
****
*What It Is:*

Valuing complexity for its own sake — creating unnecessarily complex systems, using jargon when plain language works, designing for experts when regular people could be served.

*Why It Violates Accessibility:*

Complexity worship excludes people. It creates barriers. It confuses difficulty with quality. It serves ego, not users.

*Warning Signs:*

* Pride in complexity
* "It's supposed to be hard"
* Jargon used when simpler terms exist
* Resistance to simplification
* Dismissing accessibility as "dumbing down"
****

=== Gatekeeping

[sidebar]
****
*What It Is:*

Maintaining barriers that keep people out — whether through required expertise, exclusive language, insider knowledge, or intentional obscurity.

*Why It Violates Accessibility:*

Gatekeeping contradicts Kingdom values. Jesus criticized those who "shut up the kingdom of heaven against men" (Matthew 23:13). Knowledge hoarded is knowledge wasted.

*Warning Signs:*

* "You have to earn access"
* Insider language maintained
* Documentation intentionally sparse
* Community exclusive rather than welcoming
* Help conditional on proving worthiness
****

=== Expert Assumptions

[sidebar]
****
*What It Is:*

Assuming users have expertise they don't have — skipping foundational explanation, using unexplained jargon, building on assumed knowledge.

*Why It Violates Accessibility:*

Expert assumptions exclude the people who most need what we build. They create invisible barriers. They mistake exclusion for quality.

*Warning Signs:*

* Documentation starting at advanced level
* No glossary or explanation of terms
* Prerequisites unstated
* "This is obvious"
* Impatience with basic questions
****

== Decision Test

=== The Question

[IMPORTANT]
====
*"Can regular people understand this?"*

This question tests whether what we create is genuinely accessible or only accessible to those already expert.
====

=== Applying the Test

[cols="1,3",options="header"]
|===
|Situation |How to Apply

|*Writing documentation*
|Would someone unfamiliar understand this?

|*Designing interface*
|Could a first-time user navigate this?

|*Setting price*
|Can target audience afford this?

|*Explaining concept*
|Does this require prior expertise?

|*Building feature*
|Is complexity hidden from user?

|===

=== Accessibility Levels

[cols="1,3",options="header"]
|===
|Level |Description

|*Approachable*
|Not intimidating to try

|*Usable*
|Can accomplish basic tasks

|*Learnable*
|Can grow in capability

|*Mastered*
|Can use advanced features

|*Teachable*
|Can help others learn

|===

'''

== Practical Applications

=== Code and Language Design

[cols="1,2,2",options="header"]
|===
|Element |Accessible Approach |Inaccessible Approach

|*Syntax*
|Sentence-based, readable
|Symbolic, cryptic

|*Naming*
|Descriptive, plain language
|Abbreviated, coded

|*Error messages*
|Helpful explanation
|Error code only

|*Learning path*
|Progressive, scaffolded
|All at once

|===

=== Documentation

[cols="1,2,2",options="header"]
|===
|Element |Accessible Approach |Inaccessible Approach

|*Language*
|Plain, defined terms
|Jargon assumed known

|*Structure*
|Progressive complexity
|Expert level throughout

|*Examples*
|Relatable, practical
|Abstract, complex

|*Glossary*
|Provided, linked
|Terms undefined

|===

=== Product Design

[cols="1,2,2",options="header"]
|===
|Element |Accessible Approach |Inaccessible Approach

|*Onboarding*
|Guided, simple start
|Configuration required

|*Interface*
|Self-explaining
|Training required

|*Features*
|Progressive disclosure
|All visible at once

|*Help*
|Contextual, available
|Separate, manual-based

|===

=== Economic Accessibility

[cols="1,2,2",options="header"]
|===
|Element |Accessible Approach |Inaccessible Approach

|*Pricing*
|Scaled to audience ability

|*Entry*
|Free tier or low entry
|High initial cost

|*Payment*
|Flexible options
|Full payment only

|Premium gates essential features

|===

== The OmniCode Example

=== Accessibility in Action

OmniCode embodies this value:

[cols="1,3",options="header"]
|===
|Aspect |How OmniCode Implements Accessibility

|*Syntax*
|Sentence-based — reads like natural language

|*Learning*
|Non-programmers can read and understand

|*Progression*
|From readable to expert over time

|*Compilation*
|Produces code in multiple languages

|===

=== Sample Comparison

[source]
----
// Traditional programming:
if (user.age >= 18 && user.verified == true) {
    grantAccess(user.id);
}

// OmniCode approach:
When the user is at least 18 years old and the user is verified,
grant access to the user.
----

The OmniCode version is readable by anyone, not just programmers.
