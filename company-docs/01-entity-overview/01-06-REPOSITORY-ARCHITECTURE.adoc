== Repository Hierarchy

=== Overview

CWS work is organized in a hierarchy of Git repositories with submodule relationships:

[source]
----
CWS Repo (Creative Workz Studio — company level)
│
└── Bereshit Repo (Kingdom Technology foundation)
    │
    ├── CPI-SI for Claude Repo (AI integration framework)
    │
    └── Cornerstone Repo (Game engine)
----

=== Hierarchy Principles

[cols="1,3",options="header"]
|===
|Principle |Application

|*Parent Contains Child*
|Higher-level repos include lower-level as submodules

|*Child Can Stand Alone*
|Each repo is complete and functional independently

|*Clear Ownership*
|Each repo has defined ownership and responsibility

|*Shareable Components*
|Submodules can be shared with external parties without exposing parent

|*Version Pinning*
|Parent pins specific versions of submodules for stability
|===

'''

== Submodule Architecture

=== What Are Submodules

Git submodules allow one repository to include another at a specific version:

* Parent repo references child repo at a specific commit
* Child repo maintains full independence
* Parent can update to newer child versions deliberately
* Changes to child don't automatically affect parent

=== Submodule Benefits

[cols="1,3",options="header"]
|===
|Benefit |Description

|*Version Stability*
|Parent pins specific version; unexpected changes don't break parent

|*Independent Development*
|Child repo can evolve without coordinating every change

|*Selective Sharing*
|Can share child without exposing parent

|*Clear Boundaries*
|Defined interfaces between components

|*Distributed Ownership*
|Different teams can own different repos
|===

=== Submodule Practices

[cols="1,3",options="header"]
|===
|Practice |Description

|*Pin to Stable*
|Parent should reference tested, stable child versions

|*Deliberate Updates*
|Update child references intentionally, not automatically

|*Document Versions*
|Track why specific versions are pinned

|*Test After Updates*
|Verify parent still works after child version updates

|*Coordinate Breaking Changes*
|Communicate when child changes break parent expectations
|===

== Code Organization Principles

=== Layered Architecture (L0-L5)

Code within Bereshit follows the layered architecture:

[source]
----
word/work/
├── pkg/
│   ├── trit/         (L0 — Universal)
│   ├── omni/         (L1 — OmniCode)
│   ├── fuse/         (L2 — Platform/Filesystem)
│   ├── foundation/   (L0/L3 — Core foundations)
│   └── ...
├── cmd/              (CLI tools)
└── ...
----

=== Dependency Direction

[IMPORTANT]
====
*Dependency Rule:* Higher layers depend on lower layers. Lower layers NEVER depend on higher layers.

* L5 may import L4, L3, L2, L1, L0
* L4 may import L3, L2, L1, L0
* L3 may import L2, L1, L0
* L2 may import L1, L0
* L1 may import L0
* L0 depends on nothing (foundational)
====

=== Module Organization

Each module should:

[cols="1,3",options="header"]
|===
|Principle |Application

|*Single Responsibility*
|One clear purpose per module

|*Clear Interface*
|Defined public API, hidden implementation

|*Documentation*
|README, code comments, usage examples

|*Tests*
|Unit tests, integration tests as appropriate

|*Independence*
|Minimal dependencies, especially across layers
|===

'''

=== Commit Standards

Commits follow structured format:

[source]
----
[scope] TYPE: Brief description

## Changes
- Specific change 1
- Specific change 2

## Version
version: X.Y.Z

## Understanding
Why this change was made, what was learned.

## Impact
Impact: Isolated | Cross-component | Repo-wide

## References
refs: related-items
part: which-part-of-project
----

==== Commit Types

[cols="1,3",options="header"]
|===
|Type |Use

|*INIT*
|Initial creation

|*BUILD*
|Build system, compilation changes

|*REFACTOR*
|Restructuring without changing behavior

|*EXPAND*
|Adding new capabilities

|*FIX*
|Bug fixes

|*DOCS*
|Documentation changes

|*SYNC*
|Submodule updates

|*REORG*
|Reorganization

|*PLAN*
|Planning documents
|===

=== Documentation Co-location

Documentation lives with code:

[cols="1,3",options="header"]
|===
|Principle |Application

|*README per directory*
|Each significant directory has README

|*Code comments*
|Explain why, not just what

|*Specification co-location*
|TOML specs near implementations

|*Journey documentation*
|Devlogs capture decision history

[cols="1,2,2",options="header"]

|Go component builds

|===

=== Build Layers

Builds proceed in dependency order:

[source]
----
L0 (libtrit)           ← No dependencies
    ↓
L1 (libomni)           ← Depends on L0
    ↓
L2 (MillenniumOS, FS)  ← Depends on L0, L1
    ↓
L3 (CPI-SI)            ← Depends on L0, L1, L2
    ↓
L4 (FaithNet)          ← Depends on L0-L3
    ↓
L5 (Cornerstone, Apps) ← Depends on L0-L4
----

=== Artifact Organization

[source]
----
build/
├── lib/           # Libraries

│   └── ...
├── bin/           # Executables
│   ├── cpisi
│   ├── millenniumos

== Security Considerations

=== Repository Access

[cols="1,2",options="header"]
|===
|Level |Access

|*Public*
|Open source components intended for sharing

|*Internal*
|CWS team access only

|*Restricted*
|Sensitive components, limited access
|===

=== Sensitive Content

Never commit:

* API keys or secrets
* Passwords or credentials
* Private keys
* Personal information
* Proprietary third-party content

Use:

* Environment variables for secrets
* .gitignore for sensitive files
* Secret management tools
* Separate secure storage for credentials
