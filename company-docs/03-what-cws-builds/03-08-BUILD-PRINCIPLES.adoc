== Document Purpose

This document establishes the *principles that govern how CWS builds*—the philosophy and practices that shape all our technical work. These principles ensure our builds reflect Kingdom values and serve Kingdom purposes.

[NOTE]
====
Principles guide decisions when no explicit rule exists. Understanding *why* we build the way we do enables making good decisions in novel situations.
====

'''

== The Five Build Principles

=== Overview

All CWS builds follow five core principles:

[cols="1,2",options="header"]
|===
|Principle |Essence

|*1. Genesis Patterns*
|Architecture reflects creation order

|*2. Accessibility*
|Technology understandable by regular people

|*3. Self-Hosting*
|Minimize dependencies on external systems

|*4. Bible as Foundation*
|Scripture grounds everything

|*5. Teaching Through Making*
|Everything we build teaches
|===

'''

== Principle 1: Genesis Patterns

=== The Pattern Source

[quote, Genesis 1:1]
____
In the beginning God created the heaven and the earth.
____

Architecture follows patterns from Genesis because:

* Creation patterns are *divinely established*, not arbitrary
* Following creation order produces *coherent systems*
* Genesis reveals *principles* applicable beyond biology
* Creation patterns are *universal*—they apply to all making

=== Pattern Applications

==== Ternary Foundation

Based on Genesis 1:6 (firmament dividing waters):

[cols="1,1,2",options="header"]
|===
|Value |Genesis Element |Application

|*-1*
|Waters below / Formless
|Undefined, raw, potential (void/)

|*0*
|Firmament / Dividing line
|Structure, boundary, definition (word/)

|*+1*
|Waters above / Complete
|Verified, whole, good (tov/)
|===

==== Creation Order

Layers built in order, each depending on what came before:

[cols="1,1,2",options="header"]
|===
|Creation Day |What Created |Stack Parallel

|*Day 1*
|Light, day/night separation
|L0: Foundation, basic distinctions

|*Day 2*
|Firmament, waters divided
|L1: Language structure

|*Day 3*
|Dry land, vegetation
|L2: Platform, growing systems

|*Day 4*
|Sun, moon, stars
|L3: Governing intelligence

|*Day 5*
|Sea creatures, birds
|L4: Communication, networking

|*Day 6*
|Land animals, mankind
|L5: Applications, users
|===

==== Formless to Form

Development follows the pattern from Genesis 1:2—moving from formless to formed:

[source]
----
FORMLESS → FORMED:

void/                  word/                  tov/
(tohu - formless)  →  (davar - word)      →  (tov - good)

Ideas               →  Structure          →  Complete
Potential           →  Definition         →  Verified
Raw                 →  Processed          →  Ready
----

=== Why This Matters

[cols="1,3",options="header"]
|===
|Benefit |Explanation

|*Coherence*
|Following divine pattern produces integrated systems

|*Teaching*
|Architecture teaches creation principles

|*Timelessness*
|Divine patterns endure; trends pass

|*Alignment*
|Building mirrors the Creator's approach
|===

'''

== Principle 2: Accessibility

=== The Principle

Technology should be understandable by regular people, not just experts.

[quote, Habakkuk 2:2]
____
Write the vision, and make it plain upon tables, that he may run that readeth it.
____

=== What Accessibility Means

[cols="1,3",options="header"]
|===
|Aspect |Application

|*Language*
|Code reads like natural language (OmniCode)

|*Documentation*
|Clear explanations, not just technical specs

|*Architecture*
|Structure has discernible reason

|*Interfaces*
|Regular people can use the tools

|*Learning Curve*
|Approachable entry points
|===

=== Why Accessibility Matters

[cols="1,3",options="header"]
|===
|Reason |Explanation

|*Kingdom Service*
|Serve the body, not just technical elite

|*Reproduction*
|Others can learn, maintain, improve

|*Teaching*
|Technology itself can teach

|*Survival*
|If experts are gone, others can continue

|*Stewardship*
|Accessible technology is good stewardship
|===

=== Accessibility in Practice

[cols="1,2,2",options="header"]
|===
|Area |Inaccessible |Accessible (CWS)

|*Code Syntax*
|`if (x && y) { f(); }`
|`when x and y, do f`

|*Documentation*
|Technical jargon assumed
|Plain language explanation

|*Error Messages*
|`ERR_SEGFAULT 0x7fff`
|"Cannot access memory at this location because..."

|*Architecture*
|Arbitrary conventions
|Patterns with explained meaning
|===

'''

== Principle 3: Self-Hosting

=== The Principle

Minimize dependencies on external systems, especially those that could restrict access.

=== Why Self-Hosting Matters

[cols="1,3",options="header"]
|===
|Reason |Explanation

|*Independence*
|Not subject to others' decisions

|*Deplatform Resistance*
|Can't be removed from platforms you control

|*Mark-Free Operation*
|No accounts with beast-system providers required

|*Long-term Sustainability*
|Not dependent on companies that may cease operations

|*Control*
|Full understanding and control of stack
|===

=== Self-Hosting Levels

[cols="1,2,2",options="header"]
|===
|Level |Description |CWS Goal

|*Hardware*
|Own physical machines
|Where practical

|*Operating System*
|Own OS (MillenniumOS)
|Full self-hosting at L2

|*Language*
|Own programming language (OmniCode)
|Full self-hosting at L1

|*Network*
|Own network infrastructure (FaithNet)
|Full self-hosting at L4

|*Applications*
|Own applications
|Building at L5
|===

=== Self-Hosting Tradeoffs

[cols="1,2,2",options="header"]
|===
|Consideration |Tradeoff |CWS Approach

|*Effort*
|Building is more work than using
|Invest effort for independence

|*Time*
|Takes longer to build
|Long-term view justifies investment

|*Features*
|May have fewer features initially
|Essential features first; grow over time

|*Ecosystem*
|Smaller community
|Build community around Kingdom tech
|===

'''

== Principle 5: Teaching Through Making

=== The Principle

Everything we build teaches. Code comments explain why. Commits document the journey. Architecture reveals principle.

=== What Teaching Means

[cols="1,3",options="header"]
|===
|Aspect |Application

|*Code Teaches*
|Code structure reveals design thinking

|*Comments Teach*
|Explain why, not just what

|*Commits Teach*
|Document the journey and decisions

|*Architecture Teaches*
|Structure embodies principles

|*Documentation Teaches*
|Not just reference but understanding
|===

=== Why Teaching Matters

[cols="1,3",options="header"]
|===
|Reason |Explanation

|*Reproduction*
|Others can learn and continue the work

|*Preservation*
|Knowledge survives personnel changes

|*Kingdom Building*
|Equipping the body to build

|*Long-term Value*
|Teaching compounds over time

|*Obedience*
|Follows Habakkuk 2:2 imperative
|===

=== Teaching Practices

[cols="1,3",options="header"]
|===
|Practice |Implementation

|*Why Comments*
|Code comments explain rationale, not just mechanics

|*Meaningful Commits*
|Commit messages tell the story of development

== Applying Principles

=== Decision Framework

When making technical decisions, apply all five principles:

[cols="1,2",options="header"]
|===
|Question |Principle Check

|*Does this follow creation patterns?*
|Genesis Patterns

|*Can regular people understand this?*
|Accessibility

|*Does this increase or decrease external dependency?*
|Self-Hosting

|*Is this grounded in scripture?*
|Bible as Foundation

|*Does this teach or hide?*
|Teaching Through Making
|===

=== Principle Conflicts

Sometimes principles may seem to conflict:

[cols="1,2,2",options="header"]
|===
|Conflict |Example |Resolution

|Accessibility vs. Self-Hosting
|Building own language is hard
|Build with accessibility in mind; worth the effort

|Teaching vs. Shipping
|Documentation takes time
|Document alongside development, not after

|Genesis Patterns vs. Convention
|Industry uses binary
|Follow patterns; explain why different
|===

=== Principle Priorities

When principles conflict, prioritize:

. *Bible as Foundation* — Scripture always authoritative
. *Genesis Patterns* — Divine patterns trump human conventions
. *Self-Hosting* — Independence enables everything else
. *Accessibility* — Serving people matters
. *Teaching* — Long-term knowledge transfer

'''

== Principle Verification

=== Review Checklist

For any significant build decision, verify:

[%interactive]
* [ ] Architecture follows Genesis patterns where applicable
* [ ] Design is accessible to non-experts
* [ ] Dependencies minimized; self-hosting maximized
* [ ] Scriptural foundation identified and documented
* [ ] Teaching value present (comments, docs, structure)

=== Anti-Patterns

Watch for violations of principles:

[cols="1,2,2",options="header"]
|===
|Anti-Pattern |Violation |Correction

|*Arbitrary Architecture*
|No Genesis pattern basis
|Ground in creation patterns

|*Expert-Only Code*
|Inaccessible to regular people
|Simplify, document, explain

|*External Dependency*
|Unnecessary reliance on external services
|Build internal capability

|*Disconnected from Scripture*
|No biblical foundation
|Identify and document scriptural basis

|*Undocumented Code*
|Nothing teaches
|Add teaching documentation
|===

'''
