== Abstract

This document defines the migration plan for the OmniCode IDE from direct ncurses calls to the Cornerstone display abstraction layer. The goal is ONE unified codebase that works across CLI, TUI, and GUI modes.

== Current State

=== Architecture Problem

The IDE currently has two parallel implementations:

[cols="1,2,2,1"]
|===
| File | Approach | Features | Status

| `omni_ide_tui.c`
| Direct ncurses
| Complete (panels, menus, syntax)
| Default path

| `omni_ide_gui.c`
| Display abstraction
| Incomplete (missing panels)
| --gui flag path
|===

=== The Ladder Principle

----
GUI  (top)     → display_*() → gui backend     [Presentation adds]
TUI  (middle)  → display_*() → ncurses backend [Presentation adds]
CLI  (bottom)  → display_*() → text backend    [Logic lives here]
----

**Logic stays at the BOTTOM.** Presentation ADDS as you move up.

=== Verified State (2026-01-15)

* ✅ CLI fallback works - confirms ladder logic
* ✅ TUI rendering works - display_init(DISPLAY_TUI) routes to ncurses
* ✅ Phase 1 complete - lifecycle calls migrated

== Migration Phases

=== Phase 1: Lifecycle ✅ COMPLETE

[cols="1,3"]
|===
| Status | ✅ Complete (2026-01-15)

| Changes
a|
* Added `#include "display.h"` to omni_ide_tui.c
* Replaced `initscr()/raw()/noecho()/keypad()` with `display_init(&config)`
* Replaced `endwin()` with `display_shutdown()`
* DisplayConfig specifies `DISPLAY_TUI` mode

| Files Modified
| `omni_ide_tui.c` lines 27, 590-598, 646
|===


=== Phase 2: Cursor Positioning

[cols="1,3"]
|===
| Status | ⏳ Pending

| Scope
| 14 `move(y, x)` calls

| Migration
a|
[source,c]
----
// Before:
move(y, x);

// After:
display_set_cursor(x, y);  // Note: argument order differs!
----

| Notes
| Argument order: ncurses is (y,x), display layer is (x,y)
|===


=== Phase 3: Print Output

[cols="1,3"]
|===
| Status | ⏳ Pending

| Scope
| 11 `printw()` + 2 `mvprintw()` calls

| Migration
a|
[source,c]
----
// Before:
printw("text");
mvprintw(y, x, "text");

// After:
display_print("text");
display_print_at(x, y, "text");
----
|===


=== Phase 4: Styling

[cols="1,3"]
|===
| Status | ⏳ Pending

| Scope
| 15 `attron()` + 13 `attroff()` calls

| Migration
a|
[source,c]
----
// Before:
attron(COLOR_PAIR(COLOR_KEYWORD));
printw("word");
attroff(COLOR_PAIR(COLOR_KEYWORD));

// After:
DisplayStyle style = {DISPLAY_COLOR_YELLOW, DISPLAY_COLOR_DEFAULT, false};
display_print_styled("word", style);
----

| Challenge
| IDE has custom color pairs (COLOR_PRAGMA, COLOR_KEYWORD, etc.)
that need mapping to DisplayColor enum
|===


=== Phase 5: Input

[cols="1,3"]
|===
| Status | ⏳ Pending

| Scope
| 1 `getch()` call (main loop)

| Migration
a|
[source,c]
----
// Before:
int ch = getch();

// After:
DisplayKey key = display_wait_key();
----

| Notes
| Key mapping required: ncurses KEY_* → DisplayKey enum
|===


=== Phase 6: Size/Refresh

[cols="1,3"]
|===
| Status | ⏳ Pending

| Scope
| 1 `getmaxyx()` + 1 `refresh()` call

| Migration
a|
[source,c]
----
// Before:
getmaxyx(stdscr, height, width);
refresh();

// After:
display_get_size(&width, &height);
display_refresh();
----
|===


== Phase VI: Self-Hosting

[cols="1,3"]
|===
| Goal
| Edit OmniCode IDE source code IN the OmniCode IDE

| Prerequisites
a|
* Phases 1-6 complete (unified UI codebase)
* OmniCode syntax highlighting working
* File browser navigating to `word/work/pkg/omni/src/`

| Milestone
| The IDE becomes self-modifying - Kingdom Technology editing itself
|===

=== Separation Principle

[cols="1,3"]
|===
| Directory | Purpose

| `lang/`
| What OmniCode IS - compiles to libomni.a

| `ide/`
| Tool for editing OmniCode - links libomni.a + cornerstone

| `runtime/`
| Execution environment - VM, CPI-SI state machine

| `bridge/`
| Glue code connecting omni ↔ cornerstone
|===
