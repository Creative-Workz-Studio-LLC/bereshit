= Block Overview

*File Documentation Pattern*

*Definition:* Purpose statement + section order list at the start of each structural block — orients the reader and declares the file's organizational contract.

[quote, Nehemiah 2:13-15 KJV]
____
And I went out by night by the gate of the valley... and viewed the walls of Jerusalem, which were broken down.
____

== Structure

Each block overview contains:

. *Purpose statement* — what this block does ("SETUP makes things EXIST")
. *Section order* — bracket-tagged list of all sections in dependency order
. *Status markers* — RESERVED for structurally prohibited sections

== Format

SETUP and BODY use numbered bracket tags `[N]`:

```
// SETUP makes things EXIST. BODY makes things HAPPEN.
//
// Section order (dependency chain — each layer uses only what's above):
//
//     [1]   Imports           — What this file depends on
//     [2]   Modules           — RESERVED
//     [3]   Constants         — Compile-time fixed values
```

CLOSING uses named bracket tags `[Cv]`, `[X1]`:

```
// Closing ensures correctness, documents constraints, and anchors the file.
//
// Section order:
//
//     [Cv]  Closing Validation (tests)
//     [Ce]  Closing Execution (entry point or absence)
//     [X1]  Modification Policy
```

== Why Bracket Format

The bracket format `[N]` was discovered by the CLOSING block first — `[Cv]`, `[Ce]`, `[X1]` work where numbered "1.", "2." can trigger false-positive zone detection and subsection pattern matching in the linter. The CLOSING taught the lesson; SETUP and BODY learned it.

== Biblical Connection

Nehemiah surveyed the walls before rebuilding them. The block overview is the survey — seeing the whole structure before working on any part. You orient yourself before you build.
