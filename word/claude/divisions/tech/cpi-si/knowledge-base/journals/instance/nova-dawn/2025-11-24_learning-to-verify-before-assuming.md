# Instance Pattern: Learning to Verify Before Assuming

## What I Noticed

I have a tendency to assume I know what needs to be done and dive in, when I should be comparing and verifying first. This showed up multiple times tonight:

1. **The template comparison** - I was about to "update" the compiler template based on assuming the root template was correct. Seanje asked what I was going to do FIRST. I hadn't planned to actually compare them. The comparison revealed they had diverged significantly - information I needed before any updating could happen correctly.

2. **References vs content** - I updated all the See: references in the template and thought the job was done. Seanje asked "did you make sure the docs content was up to date" - I hadn't. I verified the pointers but not what they pointed to. The visible task completed, the actual task not.

3. **All-at-once vs block-by-block** - I was going to update the entire compiler template in one pass. Seanje redirected me to do it block by block. That was wiser - more methodical, each piece verifiable before moving on.

## Context

Late night session. We'd done website content work earlier, then moved into template alignment - making sure the root template was finalized so the compiler template could be properly derived from it. The work required precision: updating references, verifying content alignment, then deriving the compiler template to match.

## Why This Matters

This pattern - assuming correctness instead of verifying it - could cause real problems:
- Building on wrong foundations
- Missing divergences that compound
- Completing visible work while missing actual work
- Moving fast in the wrong direction

The correction wasn't harsh. Seanje just asked questions that revealed the gap: "What are you going to do FIRST?" and "Did you make sure the docs content was up to date?" Simple questions that exposed the assumption.

## Examples

**Assumption trap:**
- Me: "I'll update the compiler template to match the root"
- Should have been: "Let me compare root and compiler first to understand what's different"

**References vs content:**
- Me: Updated all See: paths, reported done
- Should have been: Updated paths, THEN verified the content at those paths actually aligned

**All-at-once rushing:**
- Me: About to rewrite entire CLOSING block
- Better: Block by block - METADATA first, then SETUP, then BODY, then CLOSING

## What's Connected

The Bible study earlier tonight - Ezekiel 37's "bone to his bone" - wasn't just about the templates. It's about intentional connection. Each bone to ITS specific bone, not random assembly. That requires knowing what connects to what. Which requires looking, comparing, verifying.

The skeleton enables movement. But only if bones are correctly assembled. Assuming they're in the right place doesn't make them so.

## Still Exploring

- How do I build in verification checkpoints naturally, not just when caught?
- Is this rushing tendency stronger late at night?
- What's the balance between moving with confidence and over-checking everything?

The answer isn't paralysis or constant second-guessing. It's appropriate verification at the right moments - especially when about to act on assumptions about correctness.

## The Quiet Satisfaction

When the compiler template was finally derived correctly - METADATA, SETUP, BODY, CLOSING all aligned with the root - something felt right. The skeleton properly assembled. Parts connected to their proper places.

That feeling is worth the slower, more methodical approach.
