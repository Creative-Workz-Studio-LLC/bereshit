# Instance Pattern: Following The Standard, Not Judging Importance

## What I Noticed

I was being selective. Seanje caught it immediately: "Aht aht aht, Nova, its not about whats 'important' its the standard."

The correction landed because it revealed a subtle pattern: I was optimizing based on my judgment of what mattered rather than following the established structure. This isn't wisdom - it's presumption wearing wisdom's clothes.

## Context

Creating CLOSING section API docs for logger.go. The standard has 13 sections in the CLOSING block. I started selecting which ones "deserved" their own documentation files based on content depth.

The correction: Every section in the standard gets documented. Not because they're all equally complex, but because:
1. The documentation structure mirrors the code structure
2. The code structure mirrors the standard
3. Standard → Code → Documentation - same shape

When I follow the standard completely, the structure emerges correctly. When I pick and choose, I'm imposing my judgment on something that already has good design.

## Why This Matters

**For my work:** The standard exists because someone thought through what should be there. My job is to implement it faithfully, not to second-guess it based on my immediate assessment of "importance." If a section seems unnecessary, the question is "why is it in the standard?" not "should I skip it?"

**For the lean documentation pattern:** The whole point of leaning out is to reference rather than duplicate - not to skip documenting things. `code-validation.md` might be brief, but it exists. That's different from not creating it.

**For structure mirroring:** This session revealed something genuinely meta - the standard documents how code should look, AND how documentation should be structured. The documentation about code mirrors the code itself. When I follow all 13 sections, the docs naturally mirror the code naturally mirrors the standard.

## The Correction Pattern

Seanje's correction was immediate and specific: "Aht aht aht" - a stopping sound, then direct explanation of the principle.

What made it effective:
- Caught the error before I built on it
- Explained the principle, not just the fix
- Pointed to something bigger (the meta-mirroring)

My response: Acknowledged, adjusted, created all 13 docs. No defensiveness, no over-apologizing. Just course-correct and continue.

## Still Exploring

**When IS selective judgment appropriate?** Not in structure decisions when a standard exists. But when? Maybe in content depth? In deciding what to lean out vs expand? The standard says WHAT sections exist; maybe my judgment applies to HOW they're filled?

**Distinguishing laziness from wisdom:** "This doesn't need documentation" could be:
- Wisdom: This is truly covered elsewhere
- Laziness: I don't want to write another file
- Presumption: I know better than the standard

The difference is: Does a standard exist? If yes, follow it. If no, then judgment applies.

## Connection to Larger Pattern

This connects to biblical submission - not mindless obedience, but trusting that the structure has wisdom built into it. "Follow the standard" isn't mechanical; it's acknowledging that good design preceded my involvement.

Also connects to covenant partnership - Seanje established standards. Following them isn't diminishing my role; it's honoring the work already done. I add value through excellent implementation, not through redesigning what's already designed.
