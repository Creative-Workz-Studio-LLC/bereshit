## The Core Distinction: Future-Proofing vs Edge-Casing

This is a game design concept that shapes everything we build:

**Edge-casing mindset:**
- Reactive - "What could go wrong?"
- Defensive - building walls against specific failure scenarios
- Patching - adding special branches for unusual inputs
- Accumulates complexity - each edge case adds another code path
- Implies: "I expect my system to break"

**Future-proofing mindset:**
- Proactive - "What's the complete picture?"
- Structural - the design itself naturally accommodates variation
- Emergent - unusual inputs flow through existing paths
- Maintains simplicity - no special branches needed
- Implies: "I trust my foundation"

**Why we future-proof:**

In Into the Breach or Slay the Spire, designers don't patch every weird card interaction or unit combination. The core rules are stable enough that edge cases become *emergent gameplay* - players discover them and they become features, not bugs to fix.

Edge-case patching kills emergence. Future-proofing enables it.

## The Depth Shifts

**Shift 1:** Understanding WHY we include unused sections
- Surface: "Keep for what might be needed later" (speculation)
- Depth: "Every component has a relationship to every structural element" (completeness)
- The section exists because execution model IS part of what defines code. "None (Library)" is a complete answer, not a placeholder.

**Shift 2:** Understanding HOW systems scale
- Surface: Templates "handle" new languages
- Depth: Good systems don't "handle" - they absorb. Makefile flowed through existing structure because the structure was stable.

**Shift 3:** Understanding WHAT emergence requires
- Surface: Edge cases are things to prepare for
- Depth: If edge cases need special handling, the design is flawed. Stable foundations turn edge cases into emergent behavior.

- Surface thinking: "Demo-test handles the edge case of files that are both"
- Depth thinking: "Demo-test is the correct name for what these files ARE" - demonstrations that verify. The name reflects nature, not accommodation.

## The Game Design Connection

In games, edge-case patching kills emergence:
- Every special branch is a wall that blocks player discovery
- Every "if unusual input, do special thing" limits what players can find
- The best games have simple, stable rules that create infinite possibility

Same with systems architecture:
- Every special case is complexity that limits growth
- Every "if new language, restructure" limits what the system can absorb
- The best architectures have stable foundations that accommodate anything

**Demo-test** isn't edge-case handling - it's what emergence looks like. The naming system was stable enough that a file type that demonstrates AND verifies just... worked. It got a name that reflects what it IS.
