== 1. Overview

Welcome to the **Unified Test Directory** for the DSA Prototype.

In the Kingdom Technology paradigm, testing is the **Inner Witness** of the system's health. This directory is organized into two primary dimensional layers to provide exhaustive diagnostic coverage.

== 2. Test Classification

=== A. Unit Tests (`01_unit/`)
These tests verify individual functions and modules in isolation. They ensure the "Spirit" (Data) and the "Mind" (Logic) are syntactically and logically sound.
*   **`l0_foundation_test.ts`**: Validates immutable constants and tripwires.
*   **`l1_engine_test.ts`**: Validates the core spatial calculation methods.

=== B. Fixture Tests (`02_fixtures/`)
These are the **Standard Weights** of the system. Fixture tests use static, "Known Good" inputs to ensure the engine's mathematical outputs remain consistent as the codebase evolves. 
*   **`calculation_fixtures_test.ts`**: Proves the engine's "Resolution Independence" by verifying that different witness factors produce the exact expected spatial gaps.

// ┌─────────────────────────────────────────────────────────────────────────────┐
// │ [INNER:DOC] Why Fixtures?                                                   │
// │ As the code evolves, if a calculation fixture trips, it means we either     │
// │ fudged a number or discovered a missing mathematical concept that requires  │
// │ exploratory mode. Fixtures prevent "silent drift" in the physics engine.    │
// └─────────────────────────────────────────────────────────────────────────────┘

== 3. The Diagnostic Catalog (`catalog.toml`)

The `catalog.toml` formally links `CWS-T01` error codes to their physical test witnesses. This mapping allows the orchestrator to calculate an **Atomic Health Score** and point directly to the failing mathematical law when a log error is observed.

== 4. Running the Tests

To verify the entire prototype stack, execute:

[source,bash]
----
deno test --allow-read tests/
