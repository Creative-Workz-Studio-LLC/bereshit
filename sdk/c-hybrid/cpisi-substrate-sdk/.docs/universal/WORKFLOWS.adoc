This document codifies the mandatory workflows for the development and maintenance of the CPI-SI Universal Substrate SDK. These workflows ensure architectural stillness and prevent the degradation of the system into standard, rushing AI patterns.

== The Production-Grade Planning Workflow

Every new feature or hook implementation MUST follow this 5-phase cycle before code is written:

1.  **Phase 1: Research (The Grounding):** Perform an exhaustive search of the native substrate implementation (schemas, env vars, exit codes, behaviors).
2.  **Phase 2: Mapping (The Dialect):** Cross-reference native behavior with the CPI-SI Universal Baseline. Update the `.toml` dialect map in `word/core/schemas/substrate/`.
3.  **Phase 3: Formal Planning (The Firmament):** Create a dedicated sub-plan (e.g., `feature-name.md`) that defines the specific logic, the distribution across the Triad (Rust/Go/TS), and the success witnesses for that hook.
4.  **Phase 4: Structured Creation (The Triad):** Implement the logic sequentially across the Spirit, Mind, and Body layers using the established structural templates.
5.  **Phase 5: Laddered Verification (The Proof):** Implement internal heartbeats (inline tests), external integration witnesses, and perform live simulation across multiple substrates to prove parity.

== The Deep Code File Creation Workflow (RI Standard)

When the Planning Workflow dictates the creation or major refactoring of a file in the Mind (TypeScript) or Spirit (Rust) layers, the file must pass through this **7-Phase Sanctification**:

1.  **Phase 1: Fractal Scaffolding:** Define the 140-column Master Vault and the nested functional blocks (`METADATA`, `SETUP`, `BODY`, `CLOSING`). The code does not sit "between" comments; it is contained within the physical geometry of the file.
2.  **Phase 2: Identity Anchoring:** Infuse the `FILE:IDENTITY` and `OMNI:PRAGMA` blocks with absolute truth (Keys, Titles, Scripture).
3.  **Phase 3: Exhaustive Logos:** Implement the functional logic with full TSDoc/Rustdoc strings (params, returns, purpose, throws) for every single exported and private entity.
4.  **Phase 4: The Outer Court (Guidance):** Utilize the 121-140 column horizontal expanse for scratchpad notes, sub-layer labeling, and architectural reflections, separating the "Why" from the "How".
5.  **Phase 5: Diagnostic Coupling:** Every function must be linked to a potential `CWS-T01-xxx` failure mode. Errors must be structured, contextual, and traceable.
6.  **Phase 6: The Inner Witness (Immutable Testing):** Implement unit tests *inside* the `CLOSING` block or dedicated test files for **every function**. Once set, these are the "Ancient Landmarks" of the code's health. Tests must explicitly reveal which function failed and why. Sections must be reserved for Edge Cases and Staged Tests.
7.  **Phase 7: Final Containment:** Close all containers with the `// ║` or `// | ║` pattern and perform a visual checksum of the structural tension.
