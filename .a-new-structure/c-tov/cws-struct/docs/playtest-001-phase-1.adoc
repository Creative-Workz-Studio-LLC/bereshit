== What This Phase Tests

*The pragma is a covenant.* When a file declares itself (`// #!omni
code --rust -module`), it enters into a contract with the schema. The
linter holds it accountable. The transform engine knows what to build.

This phase tests:

1. Does the score DROP when we add a pragma to an unstructured file?
2. Does the linter correctly identify what's missing?
3. Does the transform engine scaffold the structure from the pragma alone?
4. Does the score CLIMB after transform runs?

=== The Game Dev Parallel

In game design, this is the moment you go from "character without a
class" to "character with a class but no equipment." The class
declaration (pragma) activates the skill tree (schema). The character
is weaker initially — they're being held to a standard they don't yet
meet — but now the auto-equip system (transform) knows what gear to
give them.

The unclassed character (cache.rs without pragma) had a "perfect"
score because they were evaluated on nothing. The moment they pick a
class, they're evaluated on everything that class requires.

== Observations

=== The Three Operations — Confirmed

[cols="1,2,1", options="header"]
|===
| Operation | Direction | Analogy

| *lint*
| Schema → File → Score (read + evaluate)
| Examining the player's stats

| *transform*
| Schema → File → File (read + repair)
| Auto-equipping the player

| *transpile*
| Schema → File → New File (read + convert)
| Respeccing to a new class
|===

All three share the same read pipeline. All three use the same schema
hierarchy (R[50] → R[5]). The pragma activates all three.

=== Transform Is the Superpower

One command. -9 → 98. No manual code edits. The transform:

1. Parsed the unstructured 171 lines
2. Classified imports, functions, tests
3. Built 4 blocks with proper boundaries
4. Generated 43 identity fields from context
5. Created section headers, Reserved Omissions, CLOSING zones
6. Wrote 377 lines of fully structured output

The pragma is the patient's chart. The transform is the surgeon.

=== The 2-Point Gap — Schema Richness, Not Transform Capability

The remaining gap (98 vs 100) lives in Layer 3 SUBSTANCE:

*9 warnings* — `library` subtype expects subsections that graph.rs
doesn't need:

- SETUP: Constants, Error Types, Core Types (library expects them)
- BODY: Identity Access, Trait Implementations, Constructors,
  Core Logic, Queries, Output Display (library expects them)

*17 info messages* — missing concepts and required sections. The schema
expects code patterns (`conditional_match`, `error_propagation`, etc.)
that don't exist in graph.rs because it's pure free functions.

*Root cause:* graph.rs is typed as `library` but behaves as a
`module->utility` — stateless free functions, no public API, no types.
The schema's `library` form imposes expectations for a full library
(traits, constructors, queries, output formatting) that a focused
utility module doesn't need.

=== The Diagnosis Points to Phase 2

The linter told us what's wrong: *the subtype doesn't match the file's
nature.* The transform built the structure perfectly — the remaining
gap is schema classification, not structural capability.

Phase 2: Upgrade the schema with new concepts, determine the correct
subtype for graph.rs, and watch the last 2 points close.
